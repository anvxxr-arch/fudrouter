# ADR-0005 — Contracts first, envelope and generation

- **Status:** PROPOSED — this is the recommended content of Phase 1
- **Date:** 2026-10-10

## Context

The brief requires OpenAPI for the management and inference HTTP APIs, JSON Schema for Combo/Agent definitions, versioned job/result/event schemas for Go↔Rust integration, and generated TypeScript clients — while keeping existing public API behaviour backward compatible.

Reality:

- **No OpenAPI document, no JSON Schema, no generated client** anywhere in the repo.
- The SPA calls the API through a hand-written `src/lib/api.ts`.
- Backward compatibility has **no executable guard**: 44 Go unit-test files and 5 Node test files, and zero integration/E2E suites (dependency-graph V8, V9).
- The public surfaces that must not change are known and enumerable: the 7 inference routes, ~40+ `/api/admin/*` routes, the `/api/auth/*` better-auth surface, and the SSE contract.
- JSON Schema for **Combo/Agent definitions cannot be written yet** — neither feature exists (gap register §C). Schemas for non-existent payloads would be invented.

## Decision

Phase 1 is **contracts + baseline regression**, in this order:

1. **Enumerate and freeze the *existing* surface before writing any new code.** Produce an OpenAPI 3.1 document describing exactly what ships today: the 7 inference routes plus the management routes, generated by inspection, not aspiration.
2. **Write it as a compatibility lock, not documentation.** Any later diff to that document is a breaking-change signal and must be justified.
3. **Add an integration suite that exercises the frozen surface end-to-end** (inference: chat + messages + count_tokens + models; management: the admin routes; auth: session + Discord callback; and SSE, asserting the first event arrives without buffering).
4. **Schemas for Combo/Agent are deferred** until those features have implementations — deferred, not stubbed.
5. **Job/result/event schemas are deferred to ADR-0003** (no second runtime exists to version against).
6. **Generate the TypeScript client from the frozen document** and swap `src/lib/api.ts` onto it only after the integration suite is green.

## Consequences

- Positive: the restructure gains a machine-checkable definition of "not broken", which it does not have today.
- Positive: the generated client removes a whole class of drift between the SPA and the Express routes.
- Negative: writing OpenAPI for 40+ routes by inspection is real work, and it must be done against the running code (routes are registered inline in `admin.mjs`/`pages.mjs`/`public.mjs`, not in a router table — so extraction is partly manual).
- Negative: an integration suite needs a throwaway Postgres **and** a throwaway Valkey (the suite also has to prove the `VALKEY_URL unset → in-process limiter` fail-open path still works).

## Alternatives rejected

- **Write the target OpenAPI from the brief's route list** (`/console/*`, `/admin/models`, combos, agents, quotas, referrals). Those routes mostly do not exist; the document would be fiction and would "lock" a surface that was never shipped.
- **Generate the client first.** Without a frozen server-side document, a generated client enshrines today's drift instead of removing it.
- **Skip contracts, restructure directly.** Then "backward compatible" stays an opinion, and M5/M7 (module path, env consolidation) carry unverifiable risk.

## Evidence

Gap register §D, §E; `.github/workflows/ci.yml` (no integration job); Go 44 test files / Node 5 test files; `apps/react-web/src/lib/api.ts`.
